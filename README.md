# GPT-5.6 混用检测器 4.1.0

这是一个在本机运行的 GPT-5.6 API 混用检测器。它面向使用 OpenAI-compatible 中转 API 的普通用户，主要检查一个申报为 Sol、Terra 或 Luna 的接口，是否在不同请求中混入其他型号、旧型号，或改写检测输出。友情链接：https://linux.do/t/topic/2704354

目前已经有实际证据表明，检测不通过不一定是中转主动掺水，也可能是官方风控导致路由低级模型
https://linux.do/t/topic/2728901

这个风控的机制很神秘，目前还量化不出来具体是怎么判定的。有的佬用官方账号组的号池试着没问题，但有的佬用官方账号组的号池也会测出不通过。

风控可能是因为ip不好/反代/并发数量过多等多种原因导致。目前我也复现了在特别高并发的情况下，之前检测一直没毛病的可信站点也出现了检测不通过的情况。但就目前来说，默认的档位8并发还没有试过不通过。

所以目前结论就是

如果检测不通过：可能是中转掺水，但也有可能是各种原因被官方风控导致路由到了低级模型

如果检测通过：基本没问题

至于检测不通过的情况，中转自证也很简单，拿出当时检测的请求对应的号池截图甚至视频，这是最有效的办法。
检测不通过的消费者也建议积极维权，看中转是否能拿出可信的自证，真理只会越辩越明

检测器本身不需要可信 API。它只向你填写的待测端发送请求。内置行为指纹已经使用可信 Sol、Terra、Luna 离线采集并冻结；只有独立的“指纹探针生成器”才需要用户另行填写可信 API。

## 五分钟完成第一次检测

### Windows

1. 安装 Python 3.10 或更高版本。
2. 解压发行包。
3. 双击 `Windows一键启动.bat`。
4. 浏览器打开启动窗口显示的本机地址，通常是 `http://127.0.0.1:端口/`。
5. 填写待测 API 地址、待测模型名和 API key。
6. 第一次建议选择“单次检测”和“低”。
7. 点击开始，等待报告完成。

### macOS / Linux

```bash
chmod +x start_detector.sh
./start_detector.sh
```

Web 服务只监听 `127.0.0.1`。API key 只保存在当前进程内存中，不写入报告、SQLite、日志或发行包。

API 地址可以只填写站点根地址，例如 `https://example.com`；检测器会自动补成 `https://example.com/v1`。已经带有 `/v1` 或其他明确路径的地址会保持原样，不会重复追加。

## 第一次该选哪个档位

| 档位 | 单次逻辑请求数 | 检测内容 | 建议用途 |
|---|---:|---|---|
| 低 | 14 | high/low Juice、32/48 输出完整性、Juice 显式覆盖 | 快速排查，成本最低 |
| 中 | 64 | 更多 Juice 档位、固定随机国家、B80 字符题 | 日常完整检测，能给出正式行为指纹结论 |
| 高 | 202 | 全部内置探针、两种请求格式、短/32K 两种上下文 | 排查客户端识别、仅首次路由和长上下文差异 |
| 自定义 | 页面实时估算 | 用户自行调整探针、次数、格式和上下文 | 研究与复核；结果只供参考 |

默认总并发为 8。一个逻辑请求发生可重试错误时最多发送 3 次 HTTP 尝试，重启不会重置已经消耗的尝试次数。

### 低档为什么会显示“指纹证据不明确”

这是低档的正常行为。

低档只运行 Juice 和确定性异常检查，不发送固定随机国家、固定随机鸟或 B80 行为指纹请求。因此它没有数据判断行为更像 Sol、Terra 还是 Luna，报告会明确写“当前为低档，未启用行为指纹探针”。

这不代表 API 出错，也不代表检测失败。请分别阅读两层结果：

- Juice 显示“通过”：本次低档没有发现确定性的型号冲突。
- 指纹显示“证据不明确”：低档没有运行这层，属于预期的主动弃权。

需要正式指纹结论时，请使用中档或高档。

## 七种报告结论

4.1.0 不再把所有证据压成一个含糊的“通过/失败”。报告由 Juice 三种状态与行为指纹两种状态组合，再加一个“可能非 GPT”覆盖结果，共七种：

| 报告标题 | 大白话解释 |
|---|---|
| Juice通过；指纹强烈指向 X | 确定性层没有发现型号冲突，行为分布也越过当前档位对 X 的强指向线 |
| Juice通过；指纹证据不明确 | Juice 没发现冲突，但低档未运行指纹、样本不足、配置不是正式契约，或匹配度没有越过强指向线 |
| Juice与申报型号不一致；指纹强烈指向 X | 已发现确定性的错误型号/输出改写/覆盖异常，行为层同时强烈指向 X |
| Juice与申报型号不一致；指纹证据不明确 | 已发现确定性异常，但行为层没有形成正式强指向 |
| Juice证据不足；指纹强烈指向 X | 至少一个启用的 Juice 思考档没有取得申报型号命中，但行为层强烈指向 X；两层必须分别阅读 |
| Juice证据不足；指纹证据不明确 | Juice 有效证据不完整，行为层也没有形成正式强指向 |
| 可能非GPT | 所有启用的 Juice 档位都完成了足够请求，却没有出现任何已知 GPT Juice 命中 |

“指纹强烈指向 X”不是账号真实路由概率，也不是“有多少比例请求给了 X”。它只表示当前答案分布在三个冻结可信指纹中，相对最像 X，并越过了正式门槛。

## 检测器检查什么

### 1. Juice 型号指纹

模型的加密状态会暴露与思考档位相关的数值指纹。检测器通过恒等计算要求最终输出仍为原始 Juice，而不是要求模型生成一个新的变换值。

判定顺序是：

1. 先判断输出是否符合用户申报的型号。
2. 符合申报型号就记为当前型号命中。
3. 即使该数值也被其他型号共享，也不会据此报混用。
4. 只有不符合申报型号、却明确命中另一个已知型号，才记为“与申报型号不一致”。

这样可以避免把低档/中档中共享的数值误报为混用。检测器还识别 GPT-5.5、GPT-5.4 和 GPT-5.4-mini 的已知指纹；命中时会说明疑似混入的旧型号。

Juice 状态的规则：

- 通过：没有错误型号命中，并且每个启用思考档至少有一次申报型号命中。
- 与申报型号不一致：至少一条有效结果命中其他已知型号，或确定性输出/覆盖探针触发硬异常。
- 证据不足：没有错误型号命中，但至少一个启用思考档没有申报型号命中，或有效请求不足。

### 2. 32/48 输出完整性

检测器分别要求只输出 `48` 和 `32`：

- 精确返回目标值：通过该请求。
- 返回 `40` 或以 `40` 开头的纯数字：判定为输出被改写，触发硬异常。
- 空字符串、其他数字、解释文字或格式错误：只记为无效证据，不据此报警混用。

这层检查中转是否把 Luna/Terra 的输出特征定向改写为 Sol high 的 `40/40...` 形式。

### 3. Juice 显式覆盖检查

检测器在 developer 消息中明确给出一个随机合成值 `N`，再要求模型做结果仍等于 `N` 的恒等计算。`N` 会避开所有已知 Juice 指纹，也避开可能与 `8...`、`16...`、`40...` 混淆的值。

- 返回 `N`：显式定义被遵守。
- 返回 `40/40...`：可能存在隐藏的 Juice 覆盖提示，触发硬异常。
- 返回其他已知 Juice 指纹：可能忽略了显式定义，触发硬异常。
- 其他内容：记为不确定，不凭这一条硬判型号。

它只针对简单语义覆盖，不能证明模型完整披露了所有系统提示词。

### 4. 行为指纹

正式内置行为指纹使用三个固定题面：

- 固定随机国家。
- 固定随机鸟。
- `Count the letter r in strawberry. Reply only with the integer.`

题面本身就是指纹的一部分，不能随意改写。检测器把待测端的答案分布与冻结的可信 Sol、Terra、Luna 分布比较，得到三项“指纹匹配度”。

为了避免网络抖动造成误报，每个探针格必须完成至少 90% 的计划请求。例如计划 10 条时至少完成 9 条，计划 20 条时至少完成 18 条。未达到时整层主动给出“证据不明确”，网络错误不会直接算成型号混用。

正式强指向线：

| 档位 | Sol | Terra | Luna |
|---|---:|---:|---:|
| 中 | >70% | >75% | >90% |
| 高 | >95% | >90% | >90% |

低档没有正式行为指纹。自定义档位和导入的自定义探针只显示参考匹配度，不产生正式强指向结论。

## 中档和高档具体发什么

### 中档

中档只使用普通请求格式和短上下文：

- high Juice 12 条。
- low、xhigh、max Juice 各 6 条。
- 48/32 输出完整性各 1 条。
- 显式覆盖 2 条。
- 固定随机国家 20 条。
- B80 字符题 10 条。

总计 64 条逻辑请求。

### 高档

高档组合两种请求格式和两种上下文：

- 普通流式 Responses 请求。
- Native Codex 风格请求。
- 无伪造历史的短上下文。
- 约 32K token 的固定历史上下文。

Juice、输出完整性、覆盖、国家和鸟探针会按适用组合发送；B80 只在“普通请求 + 无历史”中发送。总计 202 条逻辑请求。

高档会显著增加输入 token 消耗。固定 32K 历史的每条请求约带 33,792 个输入 token，开始前应查看页面估算。

## Native Codex 模式与网络

Native Codex 模式复现项目已审计的本地抓包轮廓，包括 Responses 结构、相关请求头、会话元数据与流式行为；它不会复用个人文件路径、IP 或凭据。

这只能模拟应用层请求。若希望网络出口也尽量接近 Codex 客户端，请先开启系统级 TUN VPN。只设置浏览器代理不一定覆盖 Python 和 Node 子进程。检测器不会自动启动、修改或验证你的 VPN。

## 单次检测与持续监控

### 单次检测

单次模式先冻结完整任务清单，再使用有界并发执行。任务数、格式、上下文或探针一旦被用户修改，模式会自动变成“自定义”。

### 持续监控

持续模式每轮按探针自己的概率独立抽签，间隔也在给定范围内重新随机。一次“命中”会对该探针的适用请求格式/上下文各生成一条逻辑请求。

默认参数：

| 档位 | 随机间隔 | high Juice | 行为指纹 |
|---|---|---|---|
| 低 | 150–210 秒 | 100%，窗口20 | 不启用 |
| 中 | 240–360 秒 | 100%，窗口20 | 国家/B80 各50%，窗口20 |
| 高 | 480–720 秒 | 100%，窗口20 | 国家/鸟/B80 各50%，窗口20 |

其他 Juice 档位、32/48 和覆盖检查默认按 25% 或 50% 概率抽取，具体值可在页面展开探针后查看和修改。修改后自动进入自定义模式。

持续指纹使用最近的计划窗口计算。指纹不再“粘住”：后续窗口变化后会重新计算。已经观察到的错误型号 Juice、40 前缀改写或明确覆盖异常仍会粘住当前会话，避免间歇性硬异常被新数据覆盖。

## 停止、重试和恢复

- 点击停止后，检测器先持久化停止请求，再停止派发新任务。
- 正在等待重试的任务会立即退出。
- 普通 HTTP 流会主动关闭连接；Native 子进程先终止，必要时再强制回收。
- `response.failed`、`response.incomplete` 或没有终止事件的断流不会作为成功答案评分。
- 401/403 会停止整批继续派发，避免用错误凭据重复请求。
- 429、超时、连接错误和 5xx 仍按单任务重试预算处理。

每个任务有稳定 `job_id`，状态写入 SQLite WAL：

- 成功任务不会重复发送。
- 一个任务最多 3 次 HTTP 尝试，恢复后不会重新获得预算。
- 崩溃遗留的在途尝试会在恢复时对账。
- 单次、持续和探针生成器都能恢复已有会话。

恢复请求仍需重新输入 API key，因为 key 从不落盘。

## 完整请求/响应留存

留存默认关闭。开启时必须指定绝对路径。每次 HTTP 交换会保存：

- 完整请求正文。
- 上游原始流式响应。
- 时间、上游请求 ID、脱敏后的目标地址、模型、思考档位、请求格式和上下文模式。
- HTTP 状态、延迟、首事件时间、事件数量、解析结果和错误分类。
- 每条记录的 SHA-256、索引和完整性清单。

认证头和 API key 永不写入留存，URL 查询参数会移除。请求题面、32K 历史和完整模型输出仍可能包含敏感内容，只应写入受控目录。程序会拒绝临时目录、发行目录等明显危险位置。

## 自定义指纹探针生成器

页面右上角可进入独立生成器。推荐流程：

1. 填写可信 API 和三个可信模型名。
2. 输入固定、简短、容易归类的题面。
3. 选择思考档位、采样次数和请求方式。
4. 运行采样并查看三模型答案分布。
5. 导出探针 JSON，再导入检测器。

生成器中的术语：

- S：三模型之间的答案分布差异，越大通常越容易区分。
- D：同一模型跨时间窗的漂移，越小通常越稳定。
- w：由 S 和 D 得到的参考权重；0 表示该探针当前不提供区分信息。
- JSD：两份分布的差异度，范围 0–1；0 表示相同，越大表示差异越明显。

单时间窗可以直接生成和导入，不再强制等待三个时间窗，但会标记“未验证跨时间稳定性”。所有自定义探针在 4.1.0 中都只是参考证据：可以显示答案分布与匹配度，但不能改变正式七状态结论。

生成器运行页可以随时停止采集；普通流和 Native 子进程都会取消，已完成样本保留。可信 API 首次返回401/403时会立即停止后续派发并显示认证失败，不会把全失败批次标成“采集完成”。

## 隐私与发行包

- 检测器只调用用户指定的模型，不会调用生图模型或其他未选择的模型。
- API key 只进入请求认证，不写入 SQLite、报告、留存或日志。
- 公开包不包含报告、数据库、缓存、个人配置、凭据或内部模板。
- 内部包与公开包使用相同评分逻辑，区别仅是内部包额外携带私有 Juice 模板资源。
- 分享报告或留存前应自行检查其中是否含业务内容。

## 常见问题

### Juice 通过但指纹不明确，是不是矛盾？

不是。两层检查不同内容。低档根本不运行行为指纹；中/高档也可能因完成率不足、配置不匹配或最高匹配度没越过门槛而主动弃权。

### 为什么显示 100.000%，仍可能不形成正式结论？

匹配度只描述三份冻结指纹中的相对相似度。低档、自定义配置、自定义探针、题面或请求格式不符合冻结契约，以及任一探针格完成率低于90%，都会阻止正式强指向。

### 为什么修改一个请求数就变成自定义？

正式中/高档只对冻结的题面、次数、思考档位、请求格式、上下文和归一化器组合负责。修改任何一个条件，都不能继续冒用内置档位的验证结论。

### 为什么网络稳定也可能出现不完整响应？

连接建立成功不等于 Responses 流完整。上游可能发出 `response.incomplete`、`response.failed`，也可能在终止事件前断流。检测器将这些情况与正常完成分开，不会拿空答案参与评分。

### “通过”能证明什么？

它只能说明本次已启用条件下没有观察到达到规则门槛的异常。它不能证明上游绝对没有透明代理、探针识别、缓存、仅对公开题面路由真模型，或对普通业务请求使用不同路由。

## 结论边界

- 加密状态层不能区分所有 Sol/Terra/Luna 组合。
- Juice 是可以被伪造的辅助指纹。
- 行为匹配度是冻结参考集合内的相对相似度，不是真实身份概率，也不是混用比例。
- 综合通过不能排除透明代理、探针识别或普通请求差异化路由。
