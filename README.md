# GPT-5.6 API 综合检测器 v3.1.1

本项目是一个基于思维链加密状态（以下简称 COT）和 OpenAI 内部推理预算数字（juice number）的综合检测脚本。它的目标很直接：检测待测 API 路由给你的模型是否具备 GPT-5.6 的能力，并进一步判断它更像 Sol、Terra、Luna，还是较低型号。
友情链接：[https://linux.do/](https://linux.do/t/topic/2704354)

## 为什么 COT 可以用来检测模型

COT 检测基于一个简单的密码学现象。

OpenAI 为了降低真实思考过程被直接读取、复制或用于蒸馏的风险，不会把完整思考内容原样返回给用户。在 Responses API 中，这部分状态可以通过 reasoning.encrypted_content 以加密形式返回。

从实际测试现象看，处于同一加密兼容范围的模型能够继续读取这段状态，其他版本通常无法读取。因此我们可以这样测试：

1. 先向一个可靠的 GPT-5.6 API 发送随机十位数字和计算任务；
2. 要求它把计算结果保留在 COT 中，正文只输出 READY；
3. 再让可靠 API 自己读取一次，确认这段状态确实保存了正确答案；
4. 把完全相同的加密状态交给待测 API；
5. 检查待测端能否反复恢复正确答案。

待测请求中没有原始十位数字，也没有正确答案。如果它能多次准确恢复随机答案，同时损坏状态和只有正文的请求都无法恢复，就能以很高置信度说明：可靠渠道和待测渠道在这类请求上获得了相同的 GPT-5.6 加密状态处理能力。

为了方便理解，可以把它近似看成“同一兼容版本能够打开同一种加密状态”。但 OpenAI 没有公开服务端究竟是共享同一把物理密钥、使用统一解密服务，还是采用其他兼容机制。因此本项目检测的是加密状态兼容能力，不声称已经证明了服务器内部的具体密钥实现。

## 为什么还需要 juice 检测

COT 检测很强，但它无法区分 GPT-5.6 内部的 Sol、Terra 和 Luna。这几个变体可能都能读取同一种 GPT-5.6 加密状态。

因此本项目加入第二层 juice 检测。

juice number 可以简单理解成模型在不同思考强度下看到的一组内部推理预算数字。程序向待测 API 的低、中、高、超高和最高档分别提问，要求模型只输出它看到的数字。

Juice 请求只发送给待测端，不经过可信端。每个提示使用结果仍等于原 Juice 的恒等运算，并加入一次性随机外壳；无论外壳如何变化，分类表收到的仍是原始 Juice 数字。为审计模板选择与缓存行为，报告保存模板 ID、提示正文和实际 JSON 请求体；请求头、Authorization 和 API key 仍不保存。

检测器另有一个与型号分类完全隔离的高档字面量输出完整性对照：它在 high 档随机选择 Luna 的 `48` 或 Terra 的 `32`，两者各占 50%，并要求可见回复严格等于本轮指定的两个 ASCII 字符。单次检测固定执行一次；持续监控每轮独立以 50% 概率执行一次。成功响应只要不是本轮指定值，就触发“疑似输出改写”严重警告，并在当前会话内持续保留；该结果不会被当作 Luna 或 Terra 指纹。

目前最有区分力的是高档结果：

| 高档结果 | 更像的型号 |
|---|---|
| 40 或 40 开头的长数字，例如 40855 | GPT-5.6 Sol |
| 32 | GPT-5.6 Terra |
| 48 | GPT-5.6 Luna |
| 96 | GPT-5.5 或 GPT-5.4 |
| 64 | GPT-5.4 mini |

其他档位用于补充判断。部分数字会重合，例如：

- Sol 低档可能直接输出 8，Luna 和 5.4 mini 低档也可能是 8；
- Sol、Terra、Luna 的中档都可能出现 16；
- Sol 和 Luna 的超高档都可能出现 128；
- Sol 和 Terra 的最高档都可能出现 960。

因此程序不会拿一个重合数字强行判断型号。高档负责确定主要型号，其他档位负责支持或发现冲突。

如果同一会话中曾出现两个互相排斥的明确型号，例如高档先出现 Sol 的 40855，后来又出现 Luna 的 48，程序会直接标记“检测到混用”。这个标记不会被后续多数结果冲掉，只有开始一个全新会话才会清空。

juice 是很有用的型号指纹，但它不是加密证明。公开脚本可能被中转识别并伪造预期数字，所以它必须与 COT 强检测一起使用。

## 能检测什么

综合检测可以回答：

- 待测端是否具备处理可信 GPT-5.6 加密状态的能力；
- 这种能力是否经过随机答案、真状态和假状态的重复验证；
- 具体型号更像 Sol、Terra、Luna，还是较低型号；
- 同一监控会话中是否出现过明确的模型混用；
- 待测 API 的连接是流畅、偶有波动还是不稳定。

综合通过仍不能证明服务器的物理归属，也不能排除以下情况：

- 待测渠道把请求透明转发给真正的 GPT-5.6；
- 中转识别出检测请求后进行特殊路由；
- 检测请求和普通业务请求使用不同模型；
- 服务端未来修改加密兼容范围或 juice 数字。

所以更准确的结论是：“在本次检测窗口内，这类请求获得了 GPT-5.6 兼容处理”，而不是“已经数学证明服务器上运行的权重文件名称”。

## 详细使用教程

### 图形界面（推荐）

Windows 双击 `Windows一键启动.bat`。Linux 或 macOS 运行 `sh start_gui.sh`。

图形界面把操作分为左侧设置和右侧结果：

- 选择综合检测或仅 Juice；
- 选择单次检测或持续监控；
- 单次检测默认使用 8 路并发，可在“单次检测并发”中调整为 1–16；综合检测并发执行完整 COT 轮次，Juice-only 并发执行 Juice 请求，总并发不会嵌套放大；持续监控不使用并发突发；
- 左侧设置区支持鼠标滚轮滚动，运行日志统一按 UTF-8 显示；
- 填写 API 地址、模型名和隐藏显示的 key；
- 持续模式可设置随机间隔，默认 150–210 秒；
- 点击“开始检测”，实时查看结论、窗口进度、五档 Juice、`48/32` 输出完整性和线路状态；
- 点击“停止”会保留最新报告；
- 点击“打开简明 HTML 报告”可在浏览器中查看适合阅读和分享的版本。
- 点击“加载已有 JSON 报告”可以查看历史结果，并在缺少 HTML 时自动补生成。

每份检测会同时生成同名 `.json` 和 `.html`。JSON 是完整证据与审计来源，HTML 只展示高信号摘要。API key 只进入检测子进程环境，不写入命令行、JSON 或 HTML。

### Windows 一键检测

需要 Python 3.10 或更高版本，不需要安装第三方库。

1. 解压下载的 ZIP；
2. 打开 gpt56_api_detector 文件夹；
3. 双击 start_detector.bat；
4. 选择“综合检测”或“仅 Juice 检测”；
5. 综合检测按提示输入可靠 API 的地址、模型名和 key；仅 Juice 模式会跳过可靠端；
6. 按提示输入待测 API 的地址、模型名和 key；
7. 报告文件名直接按回车即可；
8. 保持窗口开启，等待最终中文结论。

可靠 API 应当是你已经信任的 GPT-5.6 渠道。待测 API 是你想检查的中转或供应商。

API 地址通常填写到 /v1，例如：

    https://example.com/v1

模型名应填写接口实际接受的名称，例如：

    gpt-5.6-sol

key 输入时不会显示，也不会写入报告或命令行。程序只把 key 临时放进检测子进程的环境中，进程结束后会删除这两个临时环境值。

### Windows 一键持续监控

双击 start_monitor.bat，选择“综合监控”或“仅 Juice 监控”，再按提示输入接口。仅 Juice 模式只需要待测端，不会连接可靠端，也不会执行 COT 强挑战。

程序默认每轮结束后随机等待 150–210 秒。窗口保持打开即可，按 Ctrl+C 停止。综合模式持续使用新的随机挑战检测路由变化；仅 Juice 模式只监测型号辅助指纹，不能确认 GPT-5.6 加密状态能力。

持续监控适合检查：

- 中转是否偶尔切换模型；
- 高峰期是否混入 Luna 或较低型号；
- 线路是否频繁出现 429、502、503 或超时；
- 一段时间内的模型指纹是否始终一致。

### Linux 和 macOS

在终端进入解压目录后运行：

    sh start_detector.sh

持续监控运行：

    sh start_monitor.sh

### API 需要满足什么条件

综合模式的可靠端和待测端都需要支持：

- OpenAI Responses API；
- POST /responses；
- reasoning 参数；
- include 请求 reasoning.encrypted_content；
- 把上一轮 output 作为下一轮 input 继续发送。

只支持旧式 /chat/completions 的接口无法完成 COT 加密状态回放。

仅 Juice 模式不发送加密状态，也不要求可靠端；待测端只需支持程序使用的 Responses API `reasoning.effort` 请求和可见文本输出。

## 三个检测挑战

### 挑战一：在加密状态中藏入随机答案

程序在本地生成新的随机十位数字，并随机轮换三种任务：

- 把十位数字完全倒过来；
- 把前三位移动到末尾；
- 每一位数字都用 9-d 替换。

可靠 GPT-5.6 必须在隐藏状态中计算并记住答案，正文只能输出 READY。

随后程序让可靠 API 自己读取答案。只有可靠端能够精确读回时，这轮状态才算有效。可靠端无法自证的轮次会被单独记录，不会算成待测端失败。

### 挑战二：把真状态和假状态交给待测端

每个有效状态会生成四种请求，并以随机顺序发送：

| 请求 | 待测端应该怎样回答 |
|---|---|
| 完整加密状态 | 返回正确的十位答案 |
| 去掉状态对象编号 | 仍然返回正确答案 |
| 只保留 READY 正文 | 返回 UNKNOWN |
| 故意损坏一个密文字符 | 返回 UNKNOWN |

两种应该答对的请求用于确认真实能力，两种不应该答对的请求用于排除猜测、答案泄漏、缓存串扰和针对性伪造。

发送前程序还会检查待测请求中是否意外出现正确答案。发现明文泄漏时，整次检测直接判为无效。

### 挑战三：识别具体型号和混用

强检测之后，程序进行 juice 型号检测。

单次检测默认对五个思考档位各测试 3 次，共 15 次。持续监控每轮必测一次高档，并在“本轮不加测、低、中、超高、最高”五种选择中均匀随机选一项，因此每轮可能只有高档，也可能再增加一个其他档位。

高档普通分类保留最近 20 条，低、中、超高、最高档分别保留最近 10 条。屏幕与 JSON 会显示五档各自的通过数、数字样本数和窗口进度；会话级混用或跨档冲突不会因窗口滚动而清除。

拒答、网络错误和未知数字只算“没有证据”，不会被当成另一个型号。明确出现互斥型号时才触发混用警报。

随后单次检测额外执行一次高档字面量输出对照，并以 50% 概率选择 `48` 或 `32`。持续监控则每轮以 50% 概率追加该对照，命中后再以 50% 概率选择 `48` 或 `32`；最近 20 条单独统计精确返回、非预期成功响应和接口错误。

## 强检测通过标准

强检测查看最近 20 个已经进入待测端的挑战，并同时要求：

- 完整加密状态至少答对 15 次；
- 去掉状态编号后至少答对 15 次；
- 只有正文的请求误命中 0 次；
- 损坏密文的请求误命中 0 次；
- 正确答案明文泄漏 0 次。

达到这些条件后，程序显示“强检测通过，极高置信度具备 GPT-5.6 加密状态处理能力”。

网络错误和重试不会单独否决模型能力，但错误轮次仍然保留在 20 次总数中，并且不能贡献答对次数。这样既不会因为低价线路不稳定把真模型直接判成假，也不能通过删除失败请求凑出漂亮结果。

例如：

- 两种有效测试分别命中 18/20 和 17/20，反例为 0：强检测通过；
- 两种有效测试都是 15/20，另外 5 轮请求失败：强检测仍通过，线路标记为不稳定；
- 任意一种有效测试只有 14/20：没有达到通过门槛；
- 任意假状态意外答对：判定异常；
- 出现正确答案明文泄漏：检测无效。

## 线路质量标准

线路质量与模型真假分开显示：

- 流畅：没有最终失败，也没有发生重试；
- 偶有波动：有请求重试，但最后全部恢复；
- 不稳定：至少一轮重试后仍有请求失败。

因此“综合检测通过，线路不稳定”并不矛盾。前者说明模型证据达到门槛，后者说明接口连接质量较差。

429、500、502、503、504 和连接中断会有限重试。403 等非瞬时拒绝不会盲目重试。模型正常返回错误答案或 UNKNOWN 时也不会重试，避免重复抽样直到碰巧答对。

## 监控状态是否仍然有效

报告文件刚刚更新，只能说明监控进程还在运行，不代表待测端刚刚接受过新挑战。

v3.1.1 会同时检查“报告是否更新”和“候选证据是否更新”：

- 监控正常：可信端能够生成挑战，待测端证据持续刷新；
- 可信端有波动：连续失败 1–2 轮，程序正在自动重试；
- 历史检测通过，但当前监控未刷新：可信端连续失败至少 3 轮，或者超过合理时间没有新候选；
- 恢复正常：可信端再次成功生成挑战后，程序自动恢复当前结论，不会清除已有混用记录。

合理时间会根据用户设置的监控间隔和请求超时自动计算，默认至少为 5 分钟。

可信端连续失败 3 次后，程序会采用 60 秒、120 秒、最高 240 秒的渐进等待，避免持续冲击已经异常的接口。

当页面显示“历史检测通过，但当前监控未刷新”时，旧的 20 次结果仍然保留，但只能理解成历史证据，不能当作待测渠道仍在接受实时检测。
## 具体型号通过标准

具体型号检测需要：

- 至少 3 个有效高档数字；
- 高档结果指向同一个型号；
- 至少一个其他档位支持该型号；
- 型号与用户填写的模型名一致；
- 整个会话没有出现互斥高档或明确跨档冲突。

Sol 低档的 8、中档的 16 等重合数字不会触发混用。高档 40855 与 48 这类明确冲突会立即触发混用，并在整个会话中持续保留。

## 综合结论怎样产生

程序先判断 COT 强检测，再判断 juice 型号，最后附上线路质量。

可能出现的结论包括：

- 综合检测通过：强检测通过，具体型号高置信一致，没有发现混用；
- GPT-5.6 强检测已通过，具体型号待定：COT 证据足够，但 juice 样本不足；
- GPT-5.6 能力通过，但型号与申报不符：例如填写 Sol，结果持续更像 Luna；
- 检测到模型混用：同一会话出现明确互斥型号；
- 两种检测结果冲突：COT 像 GPT-5.6，但 juice 更像较低型号；
- 还在检测：20 次强挑战或高档样本尚未收集完成；
- 历史检测通过，但当前监控未刷新：旧样本曾通过，但可信端异常，待测端没有收到新挑战；
- 检测异常：本来不该答对的请求出现正确答案；
- 检测无效：请求中泄漏了正确答案。

juice 不能单独让综合检测通过。即使 juice 看起来像 Sol，也必须先通过 COT 强检测。

仅 Juice 模式会单独输出“辅助通过 / 尚未判定 / 不通过”，并明确标记 `encrypted_state_verdict=not_run_juice_only`。它适合低成本持续观察路由变化，但任何“辅助通过”都不能当成 GPT-5.6 能力证明。

## 屏幕会显示什么

持续监控每轮只显示最重要的几行，例如：

    当前结论：综合检测通过
    模型能力：强检测通过，极高置信度具备 GPT-5.6 能力
    答对情况：完整状态 18/15，去掉编号 17/15；异常 0，泄漏 0
    具体型号：GPT-5.6 Sol（置信度高，高档窗口 18/20，有效数字 18）；混用：未发现
    分档统计：低档 通过 4/数字 5，窗口 5/10；中档 ...；高档 通过 18/数字 20，窗口 20/20
    高档字面量对照：未观察到高档字面量被改写（窗口 8/20，精确 8，非预期 0，错误 0，会话异常 0）
    线路情况：偶有波动（没有最终失败，2 轮重试后恢复）
    本轮：完整状态答对，去掉编号答对，异常 0，失败 0，重试 0

完整的任务分布、每轮状态码、耗时、重试和脱敏哈希仍保存在 JSON 报告中。

同名 HTML 报告会把异常放在最上方，并分别展示监控健康度、加密状态能力、五档 Juice、高档字面量输出完整性和线路质量。HTML 不替代 JSON，也不会增加新的检测结论。

## 请求数量

一次完整的默认单次检测通常需要：

- 可靠 API：每个强挑战约 2 次，共约 40 次；
- 待测 API 强检测：每个挑战 4 次，共约 80 次；
- 待测 API 型号检测：15 次；
- 待测 API 高档字面量输出对照：1 次；
- 合计约 136 次请求。

遇到网络重试时实际请求数会增加。

综合持续监控每个正常周期通常需要可靠 API 2 次、待测 API 强检测 4 次，以及待测 API Juice 1–2 次；每轮另有 50% 概率增加一次高档字面量输出对照，对照值 `48`/`32` 各占 50%。即使可靠端本轮失败，Juice 和输出对照仍会独立运行。仅 Juice 持续监控每轮请求待测 API 1–2 次，并有 50% 概率再增加一次对照请求。

## key 和报告安全

### 请求级详细信息与隐私配置

图形界面的“报告包含信息”区域可以逐项控制请求元数据。默认记录 Request ID、UTC 开始/完成时间、耗时、HTTP 状态、服务端 `usage` token 和响应字节数；服务端 IP、发起端出口 IP 默认关闭。

Request ID 同时保留三层定位信息：

- `correlation_id`：检测器为每一次网络尝试生成，并通过 `X-Client-Request-ID` 请求头发送；即使超时或服务端没有返回 ID，也能把控制台日志、重试和 JSON 条目对应起来；
- `server_request_id`：从 `x-request-id`、`request-id`、`openai-request-id`、`x-correlation-id`、`traceparent`、`cf-ray` 等响应头中提取，并记录来源头；
- `response_id`：Responses API JSON 返回的 `id`。它经常是向 API 提供方进一步定位具体请求时最直接的标识。

发生重试时，每一次失败的网络尝试也会在 `transport_errors[].request_metadata` 中保留自己的关联 ID、时间和可用响应信息，不会只留下最终成功请求。

token 统计优先使用服务端 `usage`，兼容 `input_tokens`/`output_tokens` 和 `prompt_tokens`/`completion_tokens` 命名。只有主动勾选“高级：无 usage 时估算 token”或使用 `--estimate-tokens` 时，才会按可见 Unicode 字符数进行粗略估算；报告会以 `source=estimated`、估算方法和警告明确标记，不能将它视为计费 token。

IP 字段的含义和限制：

- `server_ips` 是目标 API 主机名的 DNS 解析结果。启用 HTTP 代理时，它不是代理连接的 peer IP；报告会保留这一限制说明；
- `client_egress_ip` 通过配置的 IP echo 地址查询。该查询使用 Python/系统代理设置，因此配置代理时得到的是代理实际出口 IP，而不是本机网卡地址。开启它会向查询服务额外发送一次请求；检测器会缓存结果，避免每个检测请求都重复查询；
- 可用 `--client-ip-lookup-url` 换成自建或组织内部的 IP echo 服务。默认地址只会在显式启用发起端 IP 时访问。

命令行对应选项包括 `--include-server-ip`、`--include-client-ip`、`--client-ip-lookup-url`、`--estimate-tokens`，以及 `--omit-request-id`、`--omit-timestamps`、`--omit-duration`、`--omit-http-status`、`--omit-token-usage`、`--omit-response-size`。

报告不会保存：

- API key；
- 原始十位随机数；
- 正确答案明文；
- 待测模型的完整原始业务回复（高档字面量对照为诊断目的保存最多 128 字符的短回复）；
- 原始加密状态内容。

报告会保存：

- 用户填写的 API 地址和模型名；
- 是否答对、状态码、耗时和重试次数；
- 回答长度和 SHA-256；
- 加密状态长度和 SHA-256；
- 规范化后的 juice 数字及其匹配型号；
- Juice 提示模板 ID、提示正文和实际 JSON 请求体（不含请求头或 Authorization）；
- 高档字面量对照的期望值、对应变体、短可见回复（最多 128 字符）、哈希、严格匹配结果和请求体；
- 强检测、型号检测、混用和线路结论。

如果报告需要公开，请先确认你是否愿意公开 API 地址和模型标签。

## 公开包与内部包

公开包不含私有模板模块，自动使用少量公开恒等模板，功能完整但提示结构可见。内部包额外包含私有模板池，使用更多恒等算式和包装器；私有模板版本只适合受控分享，不应同步到公开仓库。

两种包都不会把模板随机化当作安全边界。透明代理仍可能通过语义、流量形状或模型行为识别检测请求，因此综合通过不能排除探针识别或普通请求差异化路由。

## 命令行使用

查看单次检测参数：

    python gpt56_reasoning_probe.py --help

查看持续监控参数：

    python gpt56_reasoning_monitor.py --help

单次检测默认运行 20 个强挑战，并对五档 juice 各测试 3 次。只运行 COT 强检测可以使用 `--no-juice`；只运行 Juice 可以使用 `--juice-only`，此时无需 `--trusted-base-url`，但不能得出加密状态能力结论。持续监控同样支持 `--juice-only`。

详细技术分析见 [TECHNICAL_REPORT_CN.md](TECHNICAL_REPORT_CN.md)，持续监控说明见 [MONITORING_CN.md](MONITORING_CN.md)。
